Key concept Knowledge structure

Map Of Content

A curated navigation hub per theme — the human-readable entry point that also gives AI a traversable path into the model.

A Map of Content is a curated hub for one theme: it does not hold the content, it holds the *routes to* the content. One file that answers "what belongs to this subject, and how does it hang together" — maintained by a human, readable by a machine.

Borrowed vocabulary (Nick Milo / LYT), used deliberately: the term is established in the PKM field, so it needs no explanation. What BTM adds is the second reader.

Why it is a BTM concept, not just a note-taking trick

Most knowledge systems have two failure modes. Either everything is filed in folders — findable only if you already know where you put it — or everything is dumped in a search index, where you retrieve fragments but never the *shape* of a subject. A MOC is the deliberate third option: a hand-made map that survives both.

The BTM twist: a MOC is written for a human *and* for an AI. The same file that lets Jaco navigate his own domain gives an agent a traversable path — from theme → key files → source data → provenance. Structured navigation beats semantic guessing, which is Structure Beats Magic applied to knowledge rather than to pipelines. An LLM turned loose on 80.000 files retrieves plausible fragments; an LLM that reads the MOC first knows what the subject *is* before it starts searching.

What makes a MOC (and what breaks it)

| Do | Don't | |---|---| | Link to source files; keep them the truth | Copy content into the MOC — it goes stale | | One theme, explicitly scoped | A catch-all "misc" MOC nobody maintains | | Say *why* a file belongs, not just *that* it does | A bare bullet list of links | | Let MOCs overlap — a file may sit in several | Force a strict tree; knowledge isn't one | | Mark it machine-readably (`type: MOC` in frontmatter) | Encode meaning only in the filename | | Retire it when the theme dies (`3-history/`) | Keep zombie hubs that mislead |

The frontmatter marker is the part people skip and shouldn't. `type: MOC` makes the whole set queryable — every hub in the system can be listed, counted, checked for staleness, and mirrored into a database. A convention that only lives in filenames is a convention an agent cannot use.

Where it fits in BTM

A MOC is the human-curated layer above the generated one. BTM generates a great deal — models, diagrams, ADRs, features, releases. Generation scales; comprehension doesn't. The MOC is where a person states what matters and why, so the generated mass stays navigable. It is the same instinct as *eat your own dogfood* and *document your own system*: the output has to remain readable by both audiences, or the volume becomes a liability.

That makes MOCs a guard rail, not decoration. When a system produces faster than a human can read, the curated map is what keeps the whole thing understandable — and keeps the AI honest about provenance, because `derived_from` links are MOC links.
