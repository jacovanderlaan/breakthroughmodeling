Caveats As Context

Record what analysts know and definitions leave out (restatements, known spikes, broken periods, how fresh is fresh enough) next to the model, so an agent inherits the caveats instead of rediscovering them the hard way.

> Record what analysts know and definitions leave out (restatements, known spikes, broken periods, how fresh is fresh enough) next to the model, so an agent inherits the caveats instead of rediscovering them the hard way.

Thomas in't Veld draws the line: a semantic layer is not a context layer. The definition of revenue tells an agent what revenue means. It does not tell it that March was restated, that the November spike is real and not a load error, or that one region's figures before 2024 come from another system. An analyst knows those things, and an agent asked the same question does not.

Caveats as Context makes that knowledge a modelled object: a dated, owned record attached to the element it concerns, whether that is a table, a metric, a source or a period. AngelList's AI analyst, described by Isin Pesch, runs on markdown documentation with exactly such a gotcha list and no semantic layer at all. Freshness belongs here too. Whether data must be real-time depends on the decision it serves, so *fresh enough* is a caveat per decision, not a platform setting.

The supply is already there. Every incident that is resolved under Incident Modeling should leave a caveat behind, and every delivery calendar exception is one. The incident records what went wrong; the caveat records what anyone reading this data from now on must know.
